# Examples

## Python standard library - logging

- [Logger.addHandler / Logger.removeHandler](https://github.com/python/cpython/blob/main/Lib/logging/__init__.py#L1698-L1716) / [Logger.callHandlers](https://github.com/python/cpython/blob/main/Lib/logging/__init__.py#L1740-L1768) / [Handler.handle](https://github.com/python/cpython/blob/main/Lib/logging/__init__.py#L1014-L1031) - `Logger` is the Subject: it keeps a `self.handlers` list that `addHandler()`/`removeHandler()` attach to and detach from, exactly like `Subject.attach()`/`detach()`. `callHandlers(record)` is the notify step - it walks `c.handlers` for the logger and every ancestor reachable through `c.parent` (while `propagate` is set), and for each qualifying handler calls `hdlr.handle(record)`, so every `Handler` subclass (`StreamHandler`, `FileHandler`, `RotatingFileHandler`, ...) is an Observer reacting to the same `LogRecord` event without the `Logger` knowing anything about how each one formats or writes it.

## SQLAlchemy - event system

- [event.listen](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/event/api.py#L39-L121) / [\_ListenerCollection.append](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/event/attr.py#L607-L610) / [\_CompoundListener.\_\_call\_\_](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/event/attr.py#L508-L514) - `event.listen(target, identifier, fn)` is the `attach()` call: it resolves an `_event_key(target, identifier, fn)` and appends `fn` into a `_ListenerCollection`'s `listeners` deque for that target/event pair, upgrading it from a lazy `_EmptyListener` on first registration. Firing the event (e.g. an ORM class reaching `after_parent_attach`, or a `Connection` about to execute) invokes the collection's `__call__(*args, **kw)`, which runs `for fn in self.parent_listeners: fn(*args, **kw)` followed by `for fn in self.listeners: fn(*args, **kw)` - notifying every registered callback, including ones inherited from a parent class/target, with the event's arguments. This decouples ORM/Core internals (the Subject) from arbitrary user callbacks (the Observers) registered via `@event.listens_for`.

## Apache Airflow - listener plugins

- [ListenerManager.add_listener / ListenerManager.hook](https://github.com/apache/airflow/blob/main/shared/listeners/src/airflow_shared/listeners/listener.py#L111-L119) / [on_task_instance_running / on_task_instance_success / on_task_instance_failed](https://github.com/apache/airflow/blob/main/shared/listeners/src/airflow_shared/listeners/spec/taskinstance.py#L34-L56) - `ListenerManager` wraps a `pluggy.PluginManager` as the Subject: `add_hookspecs(spec_module)` registers the event contract (functions like `on_task_instance_running(previous_state, task_instance)` decorated with `@hookspec`), and `add_listener(listener)` attaches an Observer plugin object after checking `self.pm.is_registered(listener)` to avoid duplicates. Notification happens through the `hook` property (`return self.pm.hook`), which Airflow's scheduler/executor call whenever a task instance transitions state - every registered plugin that implements the matching `@hookimpl` method (e.g. `on_task_instance_running`, `on_task_instance_failed`) is invoked with the same event data, letting independent listener plugins react to lifecycle events without the core scheduler knowing they exist.
