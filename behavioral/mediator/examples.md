# Examples

## Django

- [AdminSite](https://github.com/django/django/blob/main/django/contrib/admin/sites.py) / [ModelAdmin](https://github.com/django/django/blob/main/django/contrib/admin/options.py) / [RelatedFieldWidgetWrapper](https://github.com/django/django/blob/main/django/contrib/admin/widgets.py) - `AdminSite` is the Mediator and each `ModelAdmin` is a Colleague. `AdminSite.register()` stores `admin_class(model, self)` in `_registry`, so every `ModelAdmin` receives the site as `self.admin_site` and keeps no reference to other `ModelAdmin` objects. When `ModelAdmin.formfield_for_dbfield()` builds a foreign key field, it calls `self.admin_site.get_model_admin(db_field.remote_field.model)` to learn how the related model is administered. `RelatedFieldWidgetWrapper` and `ForeignKeyRawIdWidget` ask `admin_site.is_registered(rel.model)` to decide whether to render the "add related" or lookup links. The admin for `Book` never imports or instantiates the admin for `Author`. The site resolves the relation, and registering or unregistering a model changes the behavior of all related admins without editing them.

## SQLAlchemy

- [UOWTransaction](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/orm/unitofwork.py) / [DependencyProcessor](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/orm/dependency.py) / [Session._flush](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/orm/session.py) - `Session._flush()` creates a `UOWTransaction`, registers every new, dirty and deleted object with `flush_context.register_object()`, then calls `flush_context.execute()`. `UOWTransaction` is the Mediator for one flush. The relationship-level `DependencyProcessor` subclasses (`OneToManyDP`, `ManyToOneDP`, `ManyToManyDP`) and the save and delete actions (`_SaveUpdateAll`, `_DeleteAll`, `_ProcessAll`) are the Colleagues. They never call each other. Each processor calls `uow.register_preprocessor()` and `uow.dependencies.update()` to declare which action must run before which, and `UOWTransaction.execute()` topologically sorts those declarations and runs the actions in a valid order. The ordering rules between unrelated mappers stay out of the processors, which only talk to the transaction object.

## Click

- [Context](https://github.com/pallets/click/blob/main/src/click/core.py) / [Command](https://github.com/pallets/click/blob/main/src/click/core.py) / [Parameter](https://github.com/pallets/click/blob/main/src/click/core.py) - `Context` is a per-invocation object that every `Command`, `Group` and `Parameter` receives instead of holding references to one another. `Parameter.handle_parse_result()` writes each processed value into `ctx.params`, and later parameters, callbacks (signature `callback(ctx, param, value)`) and `Command.invoke()` read from the same place. A `Group` communicates with its subcommand through `ctx.invoked_subcommand` and `ctx.invoke()`, which creates a sub-context and fills in the other command's parameter defaults. `Context.forward()` lets one command call another without importing it. This is a lighter, state-centered form of Mediator. The `Context` coordinates parsing, parent and child commands, and shared `obj` and `meta` data, but it does not decide the order of work the way the two examples above do.
