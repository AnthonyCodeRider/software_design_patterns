# Examples

## CPython (C implementation)

- [list_iter and listiter_next](https://github.com/python/cpython/blob/main/Objects/listobject.c) / [\_PyListIterObject](https://github.com/python/cpython/blob/main/Include/internal/pycore_list.h) - `PyList_Type` is the Aggregate and its `tp_iter` slot is `list_iter()`, the factory method that creates a `list_iterator`. The Iterator is the separate `_PyListIterObject`, which stores only `it_seq` (a counted reference to the list) and `it_index` (the traversal position). The `PyListIter_Type` slot `tp_iternext` is `listiter_next()`. It reads one item with `list_get_item_ref(it->it_seq, index)` and advances `it_index`. When the index runs past the end, it sets `it_index` to -1, drops `it_seq`, and returns `NULL`, which the interpreter turns into `StopIteration`. Its `tp_iter` is `PyObject_SelfIter`, so an iterator is also an iterable. Each call to `iter(lst)` returns a fresh object with its own position, so several traversals of one list run independently. The caller never touches `ob_item` or the allocation size.

- [dict_iter and dictiter_iternextkey](https://github.com/python/cpython/blob/main/Objects/dictobject.c) - `dict_iter()` calls `dictiter_new(dict, &PyDictIterKey_Type)`. `dictiterobject` holds `di_dict`, the position `di_pos` in the hash table's entry array, and `di_used`, a snapshot of the dict size taken at creation. `dictiter_iternextkey`, `dictiter_iternextvalue` and `dictiter_iternextitem` are three `tp_iternext` implementations over the same state, so one aggregate offers several traversals (keys, values, items). Each one compares `di_used` with `ma_used` and raises `RuntimeError("dictionary changed size during iteration")` if they differ. The iterator walks the index and entry tables, skips deleted slots, and hands out only keys, values or `(key, value)` tuples, so callers never see the hash table layout.

## CPython (standard library)

- [Iterable](https://github.com/python/cpython/blob/main/Lib/_collections_abc.py) / [Iterator](https://github.com/python/cpython/blob/main/Lib/_collections_abc.py) / [Sequence](https://github.com/python/cpython/blob/main/Lib/_collections_abc.py) / [KeysView](https://github.com/python/cpython/blob/main/Lib/_collections_abc.py) - `Iterable` declares the abstract `__iter__()` (the Aggregate interface). `Iterator` extends it with the abstract `__next__()` and implements `__iter__()` as `return self`, which is the Iterator interface. Concrete collections use generators as the iterator class. `Sequence.__iter__` is a generator that calls `self[i]` for increasing `i` and returns on `IndexError`. `KeysView.__iter__` is `yield from self._mapping`, and `ItemsView.__iter__` and `ValuesView.__iter__` loop over the mapping's keys. The interpreter creates the generator object, which holds the position as suspended frame state, so no explicit iterator class is written.

- [FileInput](https://github.com/python/cpython/blob/main/Lib/fileinput.py) / [DictReader](https://github.com/python/cpython/blob/main/Lib/csv.py) - Both are hand-written iterators that store their own traversal state. `FileInput.__iter__()` returns `self`. `__next__()` calls `_readline()`, increments `_filelineno`, and when a file is exhausted calls `nextfile()` and continues with the next file in the list. Callers see a single stream of lines and do not know that several files are open one after another. `csv.DictReader.__iter__()` also returns `self`, and `__next__()` pulls a row from the underlying reader, tracks `line_num`, and maps fields to the header names.

## Requests

- [Response.**iter** and iter_content](https://github.com/psf/requests/blob/main/src/requests/models.py) - `Response.__iter__()` returns `self.iter_content(128)`. `iter_content()` defines an inner generator `generate()` that yields chunks from `self.raw.stream()` or `self.raw.read(chunk_size)`, and sets `_content_consumed` at the end. When the body is already cached, it uses `iter_slices(content, chunk_size)` instead. This is a generator standing in for an Iterator class. The suspended frame holds the read position, and the caller never touches the socket or urllib3 response. Each `iter_content` call returns a new traversal, but a body read from the network can be consumed only once, which is why it raises `StreamConsumedError`.

## kafka-python

- [KafkaConsumer](https://github.com/dpkp/kafka-python/blob/master/kafka/consumer/group.py) - `KafkaConsumer` is both the Aggregate and the Iterator. `__iter__()` returns `self`, and `__next__()` pulls the next record with `next(self._iterator)`. `self._iterator` is the generator created by `_message_generator_v2()`, which calls `poll()` and yields each `record` per partition after updating the subscription position. When the generator is exhausted, `__next__()` sets `_iterator = None` and starts a new poll round until `consumer_timeout_ms` passes, then raises `StopIteration`. The class combines a hand-written `__next__` with a generator, so the consumer iterates an unbounded stream of fetched batches as a flat sequence of records. Partition assignment, fetch buffers and offsets stay hidden.
