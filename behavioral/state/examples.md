# Examples

## Python standard library - http.client

- [\_CS_IDLE / \_CS_REQ_STARTED / \_CS_REQ_SENT](https://github.com/python/cpython/blob/main/Lib/http/client.py#L98-L100) / [HTTPConnection.putrequest](https://github.com/python/cpython/blob/main/Lib/http/client.py#L1198-L1235) / [HTTPConnection.endheaders](https://github.com/python/cpython/blob/main/Lib/http/client.py#L1382-L1393) / [HTTPConnection.getresponse](https://github.com/python/cpython/blob/main/Lib/http/client.py#L1446-L1509) - `HTTPConnection` is the context and `self.__state` is its state, cycling `Idle -> Request-started -> Request-sent -> Idle`. Every request-phase method is guarded by the current state and is responsible for the transition out of it: `putrequest()` only accepts `_CS_IDLE` and moves to `_CS_REQ_STARTED`, otherwise raising `CannotSendRequest(self.__state)`; `putheader()` insists on `_CS_REQ_STARTED`; `endheaders()` moves `_CS_REQ_STARTED -> _CS_REQ_SENT` or raises `CannotSendHeader()`; `getresponse()` requires `_CS_REQ_SENT` with no outstanding `__response` or it raises `ResponseNotReady(self.__state)`, and only after `response.begin()` succeeds does it drop back to `_CS_IDLE`. The whole `ImproperConnectionState` exception hierarchy exists purely to report "this operation is not legal in the state you're in" - the classic symptom of a State machine encoded on a context object. The module docstring even ships the transition table (`Idle`, `Request-started`, `Request-sent`, and the three `*-unread-response` variants) at the [top of the file](https://github.com/python/cpython/blob/main/Lib/http/client.py#L61-L68).

## Python standard library - asyncio (TLS)

- [SSLProtocolState](https://github.com/python/cpython/blob/main/Lib/asyncio/sslproto.py#L23-L28) / [SSLProtocol.\_set_state](https://github.com/python/cpython/blob/main/Lib/asyncio/sslproto.py#L496-L532) / [SSLProtocol.buffer_updated](https://github.com/python/cpython/blob/main/Lib/asyncio/sslproto.py#L438-L451) / [SSLProtocol.eof_received](https://github.com/python/cpython/blob/main/Lib/asyncio/sslproto.py#L453-L486) - `SSLProtocol` keeps a TLS connection in one of five states - `UNWRAPPED`, `DO_HANDSHAKE`, `WRAPPED`, `FLUSHING`, `SHUTDOWN` - and dispatches on it rather than on flags: the single entry point `buffer_updated()` routes freshly arrived bytes to `_do_handshake()`, `_do_read()`, `_do_flush()` or `_do_shutdown()` depending solely on `self._state`, and `eof_received()` reacts to the same event completely differently per state (abort the handshake, advance `WRAPPED -> FLUSHING`, advance `FLUSHING -> SHUTDOWN`, or ignore it). `_set_state()` is the explicit transition function: it hard-codes the legal edges (`UNWRAPPED -> DO_HANDSHAKE -> WRAPPED -> FLUSHING -> SHUTDOWN`, plus "anything -> UNWRAPPED") and raises `RuntimeError('cannot switch state from {} to {}')` for anything else, so illegal transitions fail loudly instead of corrupting the stream. A second, independent machine - [AppProtocolState](https://github.com/python/cpython/blob/main/Lib/asyncio/sslproto.py#L31-L44) (`STATE_INIT -> STATE_CON_MADE -> STATE_EOF -> STATE_CON_LOST`) - runs in parallel to guarantee the wrapped application protocol sees a well-formed callback sequence.

## h11 (the HTTP/1.1 state machine behind httpx, uvicorn and the Starlette stack)

- [ConnectionState](https://github.com/python-hyper/h11/blob/master/h11/_state.py#L249-L364) / [EVENT_TRIGGERED_TRANSITIONS](https://github.com/python-hyper/h11/blob/master/h11/_state.py#L196-L227) / [STATE_TRIGGERED_TRANSITIONS](https://github.com/python-hyper/h11/blob/master/h11/_state.py#L235-L247) / [Connection.\_get_io_object](https://github.com/python-hyper/h11/blob/master/h11/_connection.py#L320-L338) / [READERS](https://github.com/python-hyper/h11/blob/master/h11/_readers.py#L235-L250) / [WRITERS](https://github.com/python-hyper/h11/blob/master/h11/_writers.py#L136-L145) - the purest State pattern in the Python HTTP ecosystem, and deliberately so: `_state.py` opens with "Rule 1: everything that affects the state machine and state transitions must live here in this file". The states are sentinel types (`IDLE`, `SEND_RESPONSE`, `SEND_BODY`, `DONE`, `MUST_CLOSE`, `CLOSED`, `MIGHT_SWITCH_PROTOCOL`, `SWITCHED_PROTOCOL`, `ERROR`), and `ConnectionState` holds one per role (`{CLIENT: ..., SERVER: ...}`) plus a keep-alive machine and two protocol-switch machines. `process_event()` looks the `(role, state, event_type)` triple up in `EVENT_TRIGGERED_TRANSITIONS` and rejects anything absent from the table as a `LocalProtocolError`, then `_fire_state_triggered_transitions()` applies the _joint_ rules in `STATE_TRIGGERED_TRANSITIONS` (e.g. `(CLIENT: CLOSED, SERVER: DONE) -> SERVER: MUST_CLOSE`) until a fixed point. What makes it textbook State rather than just an enum: `Connection` never branches on its state to do work - `_get_io_object()` looks the current `(role, state)` up in `READERS`/`WRITERS` and installs the matching handler object (`maybe_read_from_IDLE_client`, `expect_nothing`, or a `ChunkedReader`/`ContentLengthReader`/`Http10Reader` chosen by the body framing), so `receive_data()`/`send()` simply delegate to whatever handler the current state put in `self._reader`/`self._writer`.

## SQLAlchemy (ORM)

- [InstanceState](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/orm/state.py#L105-L128) / [InstanceState.transient / pending / deleted / persistent / detached](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/orm/state.py#L229-L324) / [Session.\_save_or_update_impl](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/orm/session.py#L4355-L4359) / [Session.\_save_impl](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/orm/session.py#L4300-L4313) / [Session.\_update_impl](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/orm/session.py#L4315-L4353) - the ORM's object lifecycle is a State machine and SQLAlchemy names it as such: every mapped instance gets an `InstanceState` companion object (created by instrumentation at `__init__` time) that reports exactly one of _transient_, _pending_, _persistent_, _deleted_ or _detached_, derived from `self.key` (does it have an identity?) and `self._attached` (is it in a `Session`?). `Session` operations then dispatch on that state rather than asking the user what they want: `session.add(obj)` funnels into `_save_or_update_impl()`, which sends a keyless (transient) instance to `_save_impl()` to be registered as pending and an already-identified (detached) one to `_update_impl()` to be re-attached to the identity map - the very same call producing an `INSERT` or a re-attach depending only on the state. The illegal edges raise rather than silently misbehave (`"already has an identity - it can't be registered as pending"`, `"Instance has been deleted. Use the make_transient() function to send this object back to the transient state"`), and each legal transition fires a named event - `pending_to_persistent`, `persistent_to_deleted`, `deleted_to_persistent` - so the transitions themselves are first-class, observable objects.
