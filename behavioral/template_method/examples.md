# Examples

## Python standard library - unittest

- [TestCase.run](https://github.com/python/cpython/blob/main/Lib/unittest/case.py#L656-L719) / [TestCase.setUp](https://github.com/python/cpython/blob/main/Lib/unittest/case.py#L516-L518) / [TestCase.tearDown](https://github.com/python/cpython/blob/main/Lib/unittest/case.py#L520-L522) / [IsolatedAsyncioTestCase.setUp](https://github.com/python/cpython/blob/main/Lib/unittest/case.py#L1577-L1580) - `TestCase.run()` is the template method: it fixes the invariant skeleton of running one test - call `result.startTest`, wrap `self._callSetUp()`, `self._callTestMethod(testMethod)`, and `self._callTearDown()` in outcome-tracking context managers, run `self.doCleanups()`, then report success/failure/skip and call `result.stopTest`. The three `_call*` helpers ([`_callSetUp`](https://github.com/python/cpython/blob/main/Lib/unittest/case.py#L633-L634), [`_callTestMethod`](https://github.com/python/cpython/blob/main/Lib/unittest/case.py#L636-L648), [`_callTearDown`](https://github.com/python/cpython/blob/main/Lib/unittest/case.py#L650-L651)) simply forward to the overridable hooks `setUp()` and `tearDown()`, which default to no-ops on `TestCase`. Every test class in the ecosystem overrides only those hooks - e.g. `IsolatedAsyncioTestCase` replaces `setUp`/`tearDown` to spin up and tear down an asyncio event loop around each test - while `run()`'s algorithm itself is never touched.

## Python standard library - http.server

- [BaseHTTPRequestHandler.handle](https://github.com/python/cpython/blob/main/Lib/http/server.py#L470-L475) / [BaseHTTPRequestHandler.handle_one_request](https://github.com/python/cpython/blob/main/Lib/http/server.py#L433-L465) / [SimpleHTTPRequestHandler.do_GET](https://github.com/python/cpython/blob/main/Lib/http/server.py#L756-L762) / [SimpleHTTPRequestHandler.do_HEAD](https://github.com/python/cpython/blob/main/Lib/http/server.py#L765-L769) - `handle()` loops calling `handle_one_request()`, which is the actual template method: it reads the raw request line, calls `self.parse_request()`, then computes `mname = 'do_' + self.command` and invokes `getattr(self, mname)()` before flushing the output stream. `BaseHTTPRequestHandler` defines no `do_GET`, `do_POST`, etc. at all - they are pure primitive-operation hooks that a subclass must supply. `SimpleHTTPRequestHandler` (used by `python -m http.server`) implements `do_GET` and `do_HEAD` to serve files via `send_head()`, reusing the identical request-parsing/dispatch skeleton from the base class unchanged.

## Django

- [BaseCommand.execute](https://github.com/django/django/blob/main/django/core/management/base.py#L446-L479) / [BaseCommand.handle](https://github.com/django/django/blob/main/django/core/management/base.py#L623-L630) - `execute()` is the template method fixing the sequence every management command follows: apply `--force-color`/`--no-color` and stdout/stderr overrides, run `self.check()` system checks when `requires_system_checks` is set, run `self.check_migrations()` when required, call the hook `self.handle(*args, **options)`, and finally write the returned output (wrapping it in transaction SQL when `output_transaction` is set). `handle()` on `BaseCommand` itself just `raise NotImplementedError("subclasses of BaseCommand must provide a handle() method")` - it is the primitive operation every command must fill in. Concrete commands such as `migrate`, `makemigrations`, and `runserver` implement only `handle()` (and `add_arguments()` for CLI options); none of them override `execute()`, so the checks-then-handle skeleton runs identically for every command shipped with Django or any third-party app.

## Apache Airflow

- [PythonOperator.execute](https://github.com/apache/airflow/blob/main/providers/standard/src/airflow/providers/standard/operators/python.py#L209-L235) / [PythonOperator.execute_callable](https://github.com/apache/airflow/blob/main/providers/standard/src/airflow/providers/standard/operators/python.py#L244-L257) / [PythonVirtualenvOperator.execute_callable](https://github.com/apache/airflow/blob/main/providers/standard/src/airflow/providers/standard/operators/python.py#L1040) / [ExternalPythonOperator.execute_callable](https://github.com/apache/airflow/blob/main/providers/standard/src/airflow/providers/standard/operators/python.py#L1264) - `PythonOperator.execute()` fixes the algorithm for running a task's Python callable: merge `op_kwargs` into the templating context, resolve them via `determine_kwargs`, lazily prepare an execution-callable runner, and then delegate to the hook `self.execute_callable()` before logging the returned value. The default `execute_callable()` just calls `self.python_callable` in-process, but `PythonVirtualenvOperator.execute_callable()` overrides it to serialize the callable and run it inside a freshly built virtualenv, and `ExternalPythonOperator.execute_callable()` overrides it to run the callable in a pre-existing external interpreter - both subclasses reuse `PythonOperator.execute()`'s skeleton completely unchanged, only swapping the one hook.

## Apache Spark (PySpark ML)

- [Estimator.fit](https://github.com/apache/spark/blob/master/python/pyspark/ml/base.py#L166-L200) / [Estimator.\_fit](https://github.com/apache/spark/blob/master/python/pyspark/ml/base.py#L112-L126) / [Transformer.transform](https://github.com/apache/spark/blob/master/python/pyspark/ml/base.py#L234-L252) / [Transformer.\_transform](https://github.com/apache/spark/blob/master/python/pyspark/ml/base.py#L218-L233) / [JavaEstimator.\_fit](https://github.com/apache/spark/blob/master/python/pyspark/ml/wrapper.py#L415-L421) / [JavaTransformer.\_transform](https://github.com/apache/spark/blob/master/python/pyspark/ml/wrapper.py#L430) - `Estimator.fit()` and `Transformer.transform()` both implement the same fixed skeleton: validate the `params` argument, `self.copy(params)` if overriding params were passed, and then delegate to an `@abstractmethod` hook - `fit()` calls `self._fit(dataset)`, `transform()` calls `self._transform(dataset)`. Every ML algorithm and model in PySpark supplies only those hooks; `JavaEstimator._fit()` and `JavaTransformer._transform()` are the shared concrete overrides used by essentially all built-in algorithms (`LogisticRegression`, `StandardScaler`, `KMeans`, ...), marshalling parameters to the JVM-backed implementation and unwrapping the Java-side result, while the param-copying skeleton in `Estimator`/`Transformer` is never duplicated.
