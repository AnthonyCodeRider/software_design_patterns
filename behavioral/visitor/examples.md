# Examples

## Python standard library - ast

- [ast.NodeVisitor / ast.NodeTransformer](https://github.com/python/cpython/blob/main/Lib/ast.py) - `ast.AST` subclasses (`Module`, `FunctionDef`, `Name`, ...) are the Elements, each identified purely by its class name rather than an explicit `accept()` method. `NodeVisitor.visit(node)` builds the method name `"visit_" + node.__class__.__name__`, looks it up on itself, and calls it - falling back to `generic_visit()`, which walks every child field and recurses - so adding a new operation over the whole grammar (a linter check, a code-metrics pass, a compiler stage) means writing one new subclass with `visit_X` methods instead of touching every node class. `NodeTransformer` reuses the same dispatch but treats each `visit_X` return value as a replacement (or, if `None`, a deletion) for the visited node, turning the same mechanism into an AST-rewriting Visitor used throughout the stdlib and tooling built on it.

## SQLAlchemy

- [Visitable.\_compiler_dispatch](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/sql/visitors.py) / [SQLCompiler](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/sql/compiler.py) - Every `ClauseElement` (`Select`, `Column`, `BindParameter`, ...) is a `Visitable` tagged with a `__visit_name__` class attribute and an `_compiler_dispatch(self, visitor, **kw)` method generated by `_generate_compiler_dispatch()`; that method is the textbook `accept()` - it looks up `"visit_" + self.__visit_name__` on whatever visitor it is handed and calls it with itself as the argument. `Compiled.process()` kicks this off with `obj._compiler_dispatch(self, **kwargs)`, and `SQLCompiler` is the concrete Visitor, implementing one `visit_select`, `visit_column`, `visit_bindparam`, `visit_insert`, etc. per element type to render that node's fragment of SQL text. Because rendering logic lives entirely in the compiler rather than on the clause elements, each SQL dialect can subclass `SQLCompiler` and override individual `visit_*` methods to change how a construct is emitted without modifying `Select` or `Column` at all - new operations (compiling to a different dialect, to DDL, or to a debug string) are added as new visitors, exactly per the pattern's intent.

## Pydantic

- [GenerateJsonSchema](https://github.com/pydantic/pydantic/blob/main/pydantic/json_schema.py) - `build_schema_type_to_method()` builds a dispatch table mapping every `CoreSchema` `type` key (`'str'`, `'int'`, `'model'`, `'list'`, `'dict'`, ...) to a same-named handler such as `str_schema()`, `model_schema()`, or `list_schema()`, playing the role of the Visitor's set of `visit_ConcreteElement` methods against the family of core-schema "elements" produced by pydantic-core. `generate_inner(schema)` is the traversal entry point: it reads `schema['type']`, pulls the matching method out of `self._schema_type_to_method`, and invokes it - each handler then recurses into `generate_inner()` for any nested schemas (e.g. `list_schema` walking its item schema), building up a JSON Schema tree in lock-step with the core-schema tree. Swapping in a subclass that overrides a handful of `*_schema` methods (as pydantic itself does for OpenAPI-flavored output) yields an entirely different traversal/output without changing how core schemas are constructed - a new Visitor over the same Elements.

## Jinja2

- [NodeVisitor / NodeTransformer](https://github.com/pallets/jinja/blob/main/src/jinja2/visitor.py) / [CodeGenerator](https://github.com/pallets/jinja/blob/main/src/jinja2/compiler.py) - `jinja2.nodes.Node` subclasses (`Template`, `For`, `Output`, `Name`, ...) form the Element hierarchy produced by the template parser. `NodeVisitor.get_visitor(node)` resolves `"visit_" + node.__class__.__name__` on itself (falling back to `generic_visit`, which recurses over child nodes), the same dynamic-dispatch mechanism as `ast.NodeVisitor`. `CodeGenerator(NodeVisitor)` is the concrete Visitor used by the template compiler: it implements `visit_Template`, `visit_Block`, `visit_Extends`, `visit_For`, and dozens more, each emitting the Python source that renders that node - so compiling a template to executable code is just running one Visitor over the parsed node tree, while `NodeTransformer` (the same dispatch, but replacing nodes via return values) backs the constant-folding optimizer that runs as a separate pass before code generation.
