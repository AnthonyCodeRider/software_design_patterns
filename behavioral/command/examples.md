# Examples

## Django

- [BaseCommand.execute](https://github.com/django/django/blob/main/django/core/management/base.py#L446-L481) / [BaseCommand.handle](https://github.com/django/django/blob/main/django/core/management/base.py#L623-L630) / [ManagementUtility.execute](https://github.com/django/django/blob/main/django/core/management/__init__.py#L353-L434) - every `django-admin`/`manage.py` subcommand (`migrate`, `runserver`, `makemigrations`, ...) is a `BaseCommand` subclass, the ConcreteCommand, that packages a unit of work behind the abstract `handle()` hook (the base class's `handle()` just `raise NotImplementedError`, exactly like this repo's `Command.execute`). `ManagementUtility` is the Invoker: it never knows which command it's running, it just resolves the name via `self.fetch_command(subcommand)` and calls `run_from_argv`, which funnels into `execute()`. `execute()` is the template that performs system checks, output wrapping and transaction handling before finally delegating the real business logic to `self.handle(*args, **options)` - the receiver-side logic lives entirely inside the concrete subclass, decoupled from the utility that triggers it.

## Celery

- [Task.**call** / Task.run](https://github.com/celery/celery/blob/main/celery/app/task.py#L506-L529) / [Task.apply_async](https://github.com/celery/celery/blob/main/celery/app/task.py#L547-L568) - `@app.task`-decorated functions become `Task` subclasses whose actual work lives in `run()`, an abstract hook that the base class defaults to `raise NotImplementedError('Tasks must define the run method.')`, mirroring this repo's `Command.execute`. `__call__` is the uniform trigger a worker (the Invoker) uses to run the task synchronously: it pushes request context, then calls `self.run(*args, **kwargs)`. `apply_async`/`delay` let the same command object be serialized, queued, delayed (`countdown`/`eta`), and executed later by a completely different process - the request-as-an-object property that distinguishes Command from a plain function call.

## Apache Airflow

- [BaseOperator.execute](https://github.com/apache/airflow/blob/main/task-sdk/src/airflow/sdk/bases/operator.py#L1640-L1649) / [\_execute_task](https://github.com/apache/airflow/blob/main/task-sdk/src/airflow/sdk/execution_time/task_runner.py#L2209-L2246) - every Airflow operator (`BashOperator`, `PythonOperator`, provider operators, ...) is a ConcreteCommand: it subclasses `BaseOperator` and implements `execute(context)`, while the base class only declares the contract and `raise NotImplementedError()`. Tasks are built ahead of time as operator instances parameterized with all the arguments they need (a `bash_command`, a `python_callable`, connection ids, etc.), then handed to the scheduler and stored in the DAG - the command object is constructed long before it runs. The task runner's `_execute_task` is the Invoker: it grabs `execute = task.execute` off whichever operator instance it was given and calls it generically (`_run_execute_callable(context, execute, task)`), with no knowledge of which concrete operator, or receiver system (a database, a subprocess, an external API), is actually behind it.
