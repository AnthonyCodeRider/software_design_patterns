# Examples

## SQLAlchemy

- [LoaderStrategy](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/orm/interfaces.py#L1507-L1536) / [`_LazyLoader`, `_ImmediateLoader`, `_SubqueryLoader`, `_SelectInLoader`](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/orm/strategies.py) / [StrategizedProperty._get_strategy](https://github.com/sqlalchemy/sqlalchemy/blob/main/lib/sqlalchemy/orm/interfaces.py#L1155-L1167) - `LoaderStrategy` is the literal Strategy interface: its docstring states it "describe[s] the loading behavior of a `StrategizedProperty` object" by supplying `setup_query()` (how to modify the SQL) and `create_row_processor()` (how to populate the attribute from a result row). Concrete strategies in `orm/strategies.py` - `_LazyLoader` (`lazy="select"`, defers the query until first access), `_ImmediateLoader` (loads eagerly inline), `_SubqueryLoader`, and `_SelectInLoader` - all implement that same contract while producing completely different SQL and timing for loading a relationship. `StrategizedProperty` is the Context: it never hardcodes which loading algorithm to use, it looks the active strategy up by `strategy_key` via `_get_strategy` (falling back to `self.strategy`, the default chosen at mapper configuration time) and delegates to it, so the same `RelationshipProperty` can be switched between lazy, eager, or subquery loading per-`Query` via `.options(lazyload(...))`/`joinedload(...)` without the property's own code changing.

## Requests

- [AuthBase.`__call__`](https://github.com/psf/requests/blob/main/src/requests/auth.py#L78-L82) / [HTTPBasicAuth.`__call__`](https://github.com/psf/requests/blob/main/src/requests/auth.py#L85-L112) / [HTTPDigestAuth.`__call__`](https://github.com/psf/requests/blob/main/src/requests/auth.py#L321-L341) / [PreparedRequest.prepare_auth](https://github.com/psf/requests/blob/main/src/requests/models.py#L670-L694) - `AuthBase` declares the single-method Strategy interface (`__call__(self, r: PreparedRequest) -> PreparedRequest`) that every authentication scheme must implement; `HTTPBasicAuth` mutates the request by setting an `Authorization: Basic ...` header while `HTTPDigestAuth` runs a stateful challenge/response handshake, yet both are fully interchangeable from the caller's point of view. `PreparedRequest.prepare_auth` is the Context: it accepts whatever `auth` object (or `(user, pass)` tuple, normalized into `HTTPBasicAuth`) the client supplied, invokes it as `auth_handler(self)`, and applies the result - it has zero knowledge of basic vs. digest vs. a user-defined subclass, exactly the decoupling the pattern is meant to provide, and lets `Session.send` swap auth strategies per-request via the `auth=` kwarg.

## Apache Airflow

- [BaseExecutor._process_workloads](https://github.com/apache/airflow/blob/main/airflow-core/src/airflow/executors/base_executor.py#L316-L325) / [ExecutorLoader.load_executor](https://github.com/apache/airflow/blob/main/airflow-core/src/airflow/executors/executor_loader.py#L336-L383) - `BaseExecutor` is the Strategy interface for "how to actually run queued tasks": `_process_workloads()` is left as `raise NotImplementedError(...)`, and each execution backend (`LocalExecutor` forking worker processes, the Celery provider's `CeleryExecutor` publishing to a broker, `KubernetesExecutor` launching pods) is a ConcreteStrategy implementing that hook its own way while sharing the common `queue_workload`/`has_task` surface defined on the base class. `ExecutorLoader.load_executor` is the selection point that picks the concrete strategy purely from the `executor` setting in `airflow.cfg` (by core name, alias, or import path) and hands back a `BaseExecutor` instance; the scheduler that calls `queue_workload` and lets the executor drain its queue is the Context, and it is written once against the abstract executor without caring which concrete backend was configured.

## Django

- [BaseCache](https://github.com/django/django/blob/main/django/core/cache/backends/base.py#L58-L263) / [CacheHandler.create_connection](https://github.com/django/django/blob/main/django/core/cache/__init__.py#L39-L52) / [ConnectionProxy](https://github.com/django/django/blob/main/django/utils/connection.py#L7-L27) - `BaseCache` fixes the algorithm's interface (`get`, `set`, `delete`, `has_key`, ...) that every cache backend must honor, and the built-in backends (`LocMemCache`, `FileBasedCache`, `DatabaseCache`, `RedisCache`, plus third-party ones like `django-redis`) are interchangeable ConcreteStrategies, each swapping in a completely different storage mechanism behind identical calls. `CacheHandler.create_connection` reads the `BACKEND` dotted path out of the `CACHES` setting, imports that class with `import_string`, and instantiates it with the configured `LOCATION`/`OPTIONS` - i.e. it selects the strategy purely from configuration at startup. The module-level `cache` object is a `ConnectionProxy` (the Context): application code calls `cache.get(key)`/`cache.set(key, value)` everywhere without ever importing or naming a concrete backend, so switching from in-memory caching to Redis is a one-line settings change with no code change.
